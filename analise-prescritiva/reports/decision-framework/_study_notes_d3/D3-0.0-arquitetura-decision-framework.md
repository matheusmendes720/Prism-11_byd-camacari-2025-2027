## §1. Por que D2 não basta (prever não é decidir)

O D2 cumpre bem o papel de **fotografia preditiva** do programa:
estabelece regime de risco, calibra distribuições (GJR-GARCH,
σ PTAX = 14,86% BCB, σ lítio = 95% annual), entrega composite 71,8/100
defensável com pesos 30/30/20/20 nas 6 sessões originais. Mas ele para
exatamente onde a **decisão** começa.

A auditoria do D2 (`1_framework/D2-AUDIT.md`) identificou **10 gaps
estruturais** que impedem o Conselho de tomar uma decisão de aprovação
com confiança. Vamos citá-los porque a arquitetura D3 nasce como resposta
direta a cada um:

| # | Gap do D2 | Resposta do D3 |
|---|---|---|
| 3.1 | Interdependências entre sessões **não modeladas** | Couplings explícitos (S1↔S3, S1↔S2, S1↔S4, S3↔S4, S6→all, S10↔S1, S7→all) + 8 drill-downs v2.1 |
| 3.2 | Prescrições **sem branching condicional** | 12 decision trees + 4D Risk Map (81 combinações) |
| 3.3 | Sem **NPV / cost-benefit** por prescrição | NPV live layer (5 prescrições, 96 cenários) |
| 3.4 | Sem **counterfactual** ("e se não fizéssemos nada?") | Baseline + 4 cenários por prescrição |
| 3.5 | Triggers dispersos, sem sistema de controle | Trigger matrix 6×3 = 18 cells + 30+ regras YAML |
| 3.6 | Sem **ownership / approval gates** | RACI 17 personas + 8 gates por valor |
| 3.7 | Análise competitiva **unidirecional** | Game theory (5 players, Nash Differentiate) |
| 3.8 | Sem **MC integrado multivariado** | MC 4-shock Cholesky, VaR 4-shock = R$ 8,21 bi |
| 3.9 | Macro é **descritivo, não prescritivo** | Auto-trigger S6→S1/S2/S3/S4 (latência ≤ 5 min) |
| 3.10 | Não responde a **pergunta de decisão com sensitivity** | 96 cenários × 5 prescrições + tornado chart |

> **Atenção**: o D3 **não substitui o D2**. Ele opera continuamente sobre
> o D2, que continua sendo a fonte de composite, VaR e MC. O D3 adiciona
> 4 camadas por cima (SIGNAL, DECISION, ACTION, LEARNING) + 1 cross-cutting
> (auto-trigger).

A metáfora central (do `DECISION-FRAMEWORK.md`, §1, linha 17):

> *"D2 é o **raio-X** (estático, mostra o estado). D3 é o **sistema
> nervoso autônomo** (percebe, decide, age, aprende)."*

A diferença operacional é que **D2 produz relatório** (mensal/trimestral),
**D3 produz decisão** (diária/semanal com aprovação obrigatória por RACI).

## §2. As 5 camadas do D3 (DATA / SIGNAL / DECISION / ACTION / LEARNING)

A arquitetura D3 é um **pipeline vertical de 5 camadas funcionais** com
**feedback loop trimestral**. A Layer 1 (DATA) é o D2 inalterado; as
camadas 2-5 são o que o D3 adiciona.

### §2.2 Layer 1 — DATA (D2 vive aqui, inalterado)

Função: hospedar o D2 sem modificação. O D3 **lê** do D2 mas não escreve.

- **6 sessões originais**: S1 Câmbio, S2 Supply, S3 Regulatório (ViE),
  S4 Competitivo, S5 Partnerships, S6 Macro.
- **Composite recomputado** a cada refresh (≤ 1h após novo dado).
- **Fontes de dados** (do `D3-AUTO-TRIGGER-SPEC.md` §3):
  - **BCB SGS** (PTAX série 10813, IPCA série 433): free, intraday.
  - **MDIC Comex Stat** (commodities, balança): free, daily.
  - **ANFAVEA** (volume auto mensal): free, scraping.
  - **BNDES portal**: free, weekly check.
  - **Reuters/Bloomberg** (opcional): R$ 50-100k/ano.

**Quem opera**: time de analytics + Risk Officer.
**Cadência**: PTAX 4×/dia · macro mensal · composite ≤ 1h.

> **Conexão D2**: este layer consome exatamente `L1.0-eda-pTAX-passo-a-passo.md`
> (σ PTAX 14,86%), `L2.2-cambio-stress-test-monte-carlo.md` (MC 4-shock)
> e `L3.0-matrizes-decisao.md` (matriz S3×S6 preditiva).

### §2.3 Layer 2 — SIGNAL (a primeira coisa que D3 adiciona)

Função: traduzir o estado do D2 em **3 sinais por dimensão** (🟢 GREEN /
🟡 AMBER / 🔴 RED) + 1 **composite** agregado + 1 **macro multiplier**.

**Definição por dimensão** (de `D3-TRIGGER-MATRIX.md` §2):

| Dim | GREEN | AMBER | RED |
|---|---|---|---|
| S1 (FX PTAX) | PTAX < 5,40 ∧ vol < 18% | 5,40 ≤ PTAX < 5,80 ∧ vol 18-25% | PTAX ≥ 5,80 ∧ vol ≥ 25% |
| S2 (Supply) | VaR realized < 0,70 | 0,70-1,00 | ≥ 1,00 |
| S3 (BNDES ViE) | ViE ≥ 20% Expansão | 10-20% Continuidade / RB Parcial | ViE < 10% RB Total |
| S4 (Pricing) | Δ share ≥ 0 | Δ share −1 a −2pp | Δ share < −2pp |
| S5 (Partnerships) | 0 stakeholders em risco | 1 stakeholder | 2+ stakeholders |
| S6 (Macro) | PIB > 0 ∧ IPCA < 5 ∧ FGV > 90 | PIB −1 a 0 ∨ IPCA 5-7 ∨ FGV 80-90 | PIB < −1% 2 trim ∨ IPCA > 7 ∨ FGV < 80 |

**Composite** (soma ponderada, pesos v0.6 do `DECISION-FRAMEWORK.md` CLAUDE.md):

$$
\text{composite}_{v0.6} = \sum_{i=1}^{11} w_i \cdot \text{score}(S_i)
$$

onde:

- $\text{score}(S_i) = 50$ se GREEN, $70$ se AMBER, $85$ se RED, $95$ se CRISIS.
- Pesos $w_i$ v0.6: S1=0.18, S2=0.16, S3=0.18, S4=0.16, S5=0.10, S6=0.10,
  S7=0.05, S8=0.08, S9=0.04, S10=0.05, S11=0.05. **Soma = 1.15 → renormalizar
  para 1.00**.

**Macro multiplier** (de `D3-INTERDEPENDENCY-S6-TRIGGERS.md`):

$$
\text{multiplier}_{S6} = \begin{cases} 1.0\times & \text{se S6 GREEN} \\ 1.5\times & \text{se S6 AMBER} \\ 2.0\times & \text{se S6 RED} \end{cases}
$$

Aplicado em S1, S2, S3, S4 (rescala todas as prescrições).

**Quem opera**: analytics + Risk Officer + auto-trigger script.
**Cadência**: tempo real (alertas via Slack/email quando semáforo muda).
**Latência alvo**: detecção → notificação ≤ 5 min
(`D3-AUTO-TRIGGER-SPEC.md` §8).

> **Chef's tip**: o auto-trigger ainda não está em produção
> (T2.1 do Phase 2, Q4 2026, 8 semanas). Até lá, o trigger matrix é
> **manual via CSO** em cadência diária/semanal/mensal conforme cluster.

### §2.4 Layer 3 — DECISION (o coração do D3)

Função: dada a combinação de sinais da Layer 2, **decidir** qual ação
executar. Implementação: **12 decision trees** + 4D Risk Map (81
combinações) + 5 gates condicionais (G1-G8).

**Decision tree exemplo** (do `DECISION-FRAMEWORK.md` §2.3, com VaR
real jul/2026):

```
IF S1 = RED (PTAX > 5.50) AND S6 = GREEN (PIB > 0)
   → Ativar tranche adicional de hedge (de 50% para 75%)
   → Acelerar revisão de pricing defensivo (S4)
   → NÃO repriorizar supply chain (PIB forte sustenta demanda)
ELIF S1 = RED AND S6 = RED (PTAX > 5.50 + PIB < 0)
   → Cenário de stress máximo
   → HEDGE 100% da exposição remanescente
   → Acionar bridge financing BNDES (S3 plano B)
   → Cortar capex não-essencial em S2 (preservar liquidity)
   → Pricing defensivo vira agressivo (proteger volume)
ELSE (todos GREEN ou AMBER)
   → Plano base de D2
```

**Quem opera**: CSO + CFO + Heads funcionais (reunião semanal).
**Cadência**: semanal (status meeting) + on-demand (quando sinal muda).
**Detalhamento**: doc D3-0.1 desta base.

### §2.5 Layer 4 — ACTION (a ponte com execução)

Função: cada decisão da Layer 3 vira **action item** registrada com
**RACI completo + 8 approval gates por valor + KPI + status**.

**Schema de uma action** (do `DECISION-FRAMEWORK.md` §2.4):

| Field | Value |
|---|---|
| ID | ACT-2026-Q3-001 |
| Descrição | Acionar tranche adicional de hedge cambial (de 50% para 75%) |
| Trigger | PTAX > 5.50 em 3 dias úteis consecutivos |
| Decision owner | CFO |
| Approval gate | CEO (R$ > 50M) |
| Deadline | 5 dias úteis |
| KPI de sucesso | Hedge ratio realizado ≥ 70% até data do trigger + 10d |
| KPI de verificação | vol mensal do P&L cambial ≤ 1.5pp |
| Status | pending / in_progress / done / failed |
| Post-mortem | (preenchido 90 dias após done) |

**Quem opera**: PMO + donos de ação + CFO (gate keeper).
**Cadência**: status semanal + flash report mensal ao board.
**Detalhamento**: doc D3-0.3 desta base (NPV + action register com 39 ações).

### §2.6 Layer 5 — LEARNING (o que diferencia D3 de um dashboard)

Função: trimestralmente, comparar **previsto vs realizado** de cada KPI
de ação, recalibrar elasticidades, atualizar thresholds, documentar
**decisões que não tomamos e deveríamos** (post-mortem inverso),
repriorizar próximo trimestre.

**Quem opera**: CSO + Risk Officer + Conselho.
**Cadência**: trimestral (90 dias).
**Output primário**: `D3-RECALIBRATION-EMPIRICAL-2026.md` (recalibração C1
já feita, validando ~50% de acurácia após v0.6, com meta > 75% para v2.0).

> **Chef's tip**: a Layer 5 é o que evita que o framework vire planilha.
> Sem learning loop, o D3 seria apenas um "tracker bonito" — o que o
> diferencia é que **recalibra com base no que aconteceu**, não no que
> o modelo previu.

### §3.3 S12 — Drift cambial (proposta v2.1)

A **12ª dimensão** é uma proposta de extensão que captura um cenário não
coberto pelos triggers pontuais de S1: **depreciação sustentada do BRL**
(3+ trimestres consecutivos de PTAX subindo, com σ realizado > 18% por
90 dias).

**Definição** (proposta, ainda não validada):

$$
\text{S12 status} = \begin{cases}
\text{GREEN} & \text{se PTAX vol 6m realized} < 14\% \\
\text{AMBER} & \text{se 14\%} \leq \text{vol 6m} < 18\% \\
\text{RED} & \text{se vol 6m} \geq 18\% \text{ sustentado 90d}
\end{cases}
$$

**Diferença vs S1**: S1 detecta **triggers pontuais** (PTAX cruza 5,40 ou
5,80 em um dia); S12 detecta **regime** (vol realizada persistentemente
alta, indicando mudança estrutural). Em outras palavras: S1 = evento,
S12 = regime.

**Ações propostas para S12 RED**:

1. **Reescalar h\* baseline**: ajustar h\* em ±10pp (S12 GREEN → h\* SEM
   ajuste; S12 AMBER → h\* +5pp; S12 RED → h\* +10pp).
2. **Acelerar nacionalização**: priorizar AG-003 (70% nacional até out/2027).
3. **Acionar AG-005 (CATL LP 70%)** se ainda não executado.
4. **Repriorizar AG-DIFF-1 (LFP verticalization)** — antecipar de 2027
   para Q4 2026.

## §4. Composite v0.6 e v2.1 proposto

### §4.1 Fórmula base (v0.6)

O composite é uma **média ponderada dos scores** individuais:

$$
\text{composite} = \sum_{i=1}^{11} w_i \cdot s_i \quad \text{com} \quad \sum w_i = 1.00
$$

onde $s_i \in \{50, 70, 85, 95\}$ conforme status (GREEN/AMBER/RED/CRISIS).

**Pesos v0.6** (originais do D3, declarados em `1_framework/CLAUDE.md`):

| Dim | Peso v0.6 | Justificativa |
|---|---|---|
| S1 | 0.18 | FX é 1º contribuidor VaR isolado |
| S2 | 0.16 | Supply é 2º contribuidor (com correlação FX) |
| S3 | 0.18 | BNDES funding é binário (ViE 0% ou ViE 25%) |
| S4 | 0.16 | Pricing defensivo tem efeito multiplicativo |
| S5 | 0.10 | LP partnerships (CATL/EVE) |
| S6 | 0.10 | Macro governor (multiplier 1.0×/1.5×/2.0×) |
| S7 | 0.05 | ESG (era nominal; **subir para 0.10 em v2.1**) |
| S8 | 0.08 | Production ramp (não pode ser ignorado) |
| S9 | 0.04 | Demand upside (secundário) |
| S10 | 0.05 | Tariff (era "pessimista"; **subir para 0.10 em v2.1**) |
| S11 | 0.05 | Competition (Nash) |
| **Total** | **1.15** | **Renormalizar para 1.00** |

> **Atenção**: os pesos originais somam **1.15** — a renormalização é
> feita dividindo cada peso por 1.15. Por exemplo, S1 efetivo = 0.18/1.15
> ≈ 0.157. Esta renormalização **não estava declarada** no CLAUDE.md
> original e é uma proposta didática.

## §6. Workflow end-to-end (do dado bruto à ação)

A integração das 5 camadas se materializa num **workflow operacional** que

### §6.1 Exemplo real: PTAX 5,07 + vol 14,41% → ação AG-002 hedge 95%

- PTAX close = R$ 5,07 (abaixo de 5,40 → S1 GREEN pelo threshold pontual)

- Composite atual = 71,8 (D3 v0.6)

### §6.2 Pipeline em 7 passos

**Passo 1 — DATA (Layer 1)**: PTAX 5,07 chega via BCB SGS API série 10813,
4× por dia (10h, 13h, 16h, 18h BRT). Latência: ≤ 5 min após fechamento.

**Passo 2 — SIGNAL (Layer 2)**: o trigger engine (quando ativo) calcula:

```

```

**Passo 3 — Coupling**: o coupling **S1↔S3 (C1)** é aplicado:
- S3 = GREEN (ViE ≥ 20% Expansão)
- → h\* baseline = **30%** (constraint de VaR residual)
- → h\* expandido = 30% × 1.5× (macro multiplier AMBER) = 45%... mas
  macro multiplier é **GREEN** aqui, então h\* = **30%**.

**Passo 4 — S7 KILL SWITCH override**: S7 = RED sobrepõe. Pela
recomendação v2.1:

> "S7 RED (kill switch ativo) sobrepõe qualquer combinação S1-S6 —

Mas **hedge FX é permitido** (proteção do NPV existente). O D3
recomenda **hedge saturado em 90-95%** quando S7 RED, mesmo com S1/S3
GREEN, porque **não dá para arriscar NPV** quando o funding futuro
está comprometido.

**Passo 5 — DECISION (Layer 3)**: decision tree #4
("S1 GREEN mas S7 RED — hedge defensivo") recomenda:

```
IF S1 = GREEN AND S7 = RED
   → Hedge sizing = 90-95% (saturação defensiva)
   → Owner: Risk Officer (R) + CFO (A)
   → Approval gate: CEO (R$ > 50M)
```

**Passo 6 — ACTION (Layer 4)**: AG-002 do `D3-ACTION-PLAN.md`:

```

   Owner: Risk Officer (R) + CFO (A) + Head Treasury (Executor)

   KPI: hedge coverage ≥ 90%; VaR residual ≤ 20% margin; 4 contrapartes
   Status: PENDENTE → IN_PROGRESS quando Decision tree #4 executa
```

**Passo 7 — LEARNING (Layer 5)**: 90 dias após execução, comparar:

- **Previsto**: h\* = 95%; VaR residual ≤ 20% margin; custo R$ 30M.
- **Realizado**: ? (preencher após 31/nov/2026).

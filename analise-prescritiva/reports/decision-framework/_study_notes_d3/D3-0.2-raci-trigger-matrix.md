## §1. RACI recap (R/A/C/I definitions + 17 personas)

### §1.1 Definições RACI

A notação RACI identifica **4 tipos de participação** em cada decisão
(do `D3-RACI.md` §3.1):

| Letra | Significado | Obrigação |
|---|---|---|
| **R** | **Responsible** | Executa a tarefa; pode ser mais de uma pessoa |
| **A** | **Accountable** | Responde pelo resultado final; **uma única pessoa** por decisão |
| **C** | **Consulted** | Opinião solicitada **antes** da decisão; comunica em 2 vias |
| **I** | **Informed** | Comunicado **após** a decisão; 1 via |

**Regra de ouro**: toda decisão tem **exatamente um A** (Accountable).
Se há mais de um A, ninguém é dono. Esta regra é verificada
automaticamente pela matriz RACI.

### §1.2 Os 8 papéis (RACI cast)

Do `D3-RACI.md` §2 (versão v0.6, 11 dimensões S1-S11):

| Papel | Descrição | Cargo típico | Mandato |
|---|---|---|---|
| **Sponsor** | Conselho que aprova recursos e estratégia | Conselho BYD / Board | Aprova walk-away, demissões, venda ativos acima de R$ 280M |
| **DecisionMaker** | Aprova decisões operacionais e aloca recursos | CFO / Director | Aprova hedge sizing, budget allocation, freeze despesas |

| **Advisor** | Consultores externos que dão opinião especializada | Consultores / Assessores | Advoga posições, game theory, análise competitiva |

## §3. Approval gates por valor (R$ 1M / 10M / 100M / 500M)

Os 8 approval gates **G1-G8** (definidos em D3-0.1 §5) são **gatekeepers**
que travam o playbook. Mas para cada **decisão individual**, há um
**approval threshold** baseado em valor de gasto. Esta seção mapeia os
dois (gate × valor).

### §3.1 Threshold de aprovação por valor (do `D3-RACI.md` §5.1)

| Faixa de gasto (R$) | Aprovador único | SLA | Documentação requerida |
|---|---|---|---|
| **R$ 0 - 50k** | Analyst + RiskOwner | 24h | Email + rationale |
| **R$ 50k - 1M** | Analyst (CSO) | 24h | Memo 1 página + KPI |
| **R$ 1M - 10M** | DecisionMaker (CFO) | 48h | Business case + risk |
| **R$ 10M - 30M** | DecisionMaker (CEO) | 72h | BC + NPV + sensitivity |
| **R$ 30M - 50M** | DecisionMaker + Sponsor | 1 semana | BC + NPV + sign-off |
| **R$ 50M - 100M** | Sponsor (Audit Committee) | 2 semanas | BC + NPV + counterfactual + RACI |
| **R$ 100M - 280M** | Sponsor (Full Board) | 3 semanas | BC + external review + NPV |
| **R$ 280M - 500M** | Sponsor + Board global | 4 semanas | + external advisor + legal review |
| **R$ 500M+** | Sponsor + Board global + HQ China | 6 semanas | + HQ China sign-off + divestiture |

### §3.2 Quorum rules (decisões colegiadas)

| Faixa | Aprovadores | Quorum mínimo |
|---|---|---|
| R$ 50M - 100M | Audit Committee (3 membros) | 2/3 |
| R$ 100M - 280M | Board (5-7 membros) | 4/5 (incluindo CEO) |
| R$ 280M - 500M | Board + 1 representante HQ China | 5/7 (incluindo HQ) |
| **R$ 500M+** | **Board global + HQ China + CEO + CFO** | **6/9 (unanimity para wind-down)** |

### §3.3 Quando aplicar cada combinação (gate × threshold)

Cenários típicos (jul/2026):

- **AG-002 hedge FX 95%** (R$ 30M/ano premium): **faixa R$ 10M-30M**
  → DecisionMaker (CEO), SLA 72h, BC + NPV + sensitivity.
- **AG-005 reserva lítio + CATL LP 70%** (R$ 450M CATL + R$ 280M EVE):
  **faixa R$ 280M-500M** → Sponsor + Board global, SLA 4 semanas,
  + external advisor + legal.
- **AG-040 bridge financing R$ 800M**: **faixa R$ 500M+** →
  Sponsor + Board global + HQ China, SLA 6 semanas,
  + HQ China sign-off + divestiture analysis.
- **AG-001 resolver lista suja S7** (R$ 25M): **faixa R$ 10M-30M**
  → DecisionMaker (CEO), SLA 72h.

### §3.4 Pre-delegation em cenários RED (do `D3-RACI.md` §8.4)

Para evitar gargalos em crises:

- **CEO delega para CFO + Board Chair** em cenários RED S6.
- **CFO tem authority de até R$ 200M** (cobre committee crisis).
- **Comitê pode decidir com quorum de 3/5** (CEO ausente é OK).

## §7. Hysteresis e anti-flapping

### §7.1 O problema do flapping

Em trigger systems, **flapping** é a oscilação rápida entre estados
(GREEN ↔ AMBER ↔ RED) quando o sinal está próximo do threshold. Isso:

- Gera **alarmes falsos** (notificações spam).
- Causa **fadiga de alerta** (CSO ignora notificações).
- Desgasta **approval gates** (CFO aprova 5×/dia em vez de 1×).

### §7.2 Hysteresis: solução padrão

O D3 implementa **hysteresis** (de `D3-TRIGGER-MATRIX.md` §4): para
transicionar AMBER → GREEN, exige **confirmação sustentada** (não basta
1 leitura abaixo do threshold).

| Transição | Confirmação mínima | Justificativa |
|---|---|---|
| GREEN → AMBER | 1 leitura (latência 5 min) | rápido — queremos ação rápida |
| AMBER → RED | 2 leituras consecutivas (latência 60 min) | evita flapping perto do limite |
| RED → AMBER | **1 trimestre** (90 dias) | macro/regime é lento; evita euforia |
| AMBER → GREEN | **3 indicadores sustentados 2 trimestres** | macro é lento; reverter custa caro |

### §7.3 Cooldown por regra

Do `D3-AUTO-TRIGGER-SPEC.md` §5.1: cada regra tem um **cooldown**
mínimo entre notificações sucessivas:

```yaml
- id: rule-001
  cooldown: 24h  # notificar 1× per day mesmo se condição persistir
```

Cooldowns típicos:

- **Regras críticas (kill switches)**: cooldown 1h.
- **Regras de transição AMBER**: cooldown 24h.
- **Regras de monitoramento (GREEN)**: cooldown 7 dias (semanal).

### §7.4 Validação cruzada (correlation check)

Em v2.1, antes de disparar, o trigger engine verifica **se a leitura
não é espúria** via correlation check:

- Se PTAX cruza threshold mas lítio não cruza (e ρ_FX,Supply = 0.4),
  verificar se o choque FX é isolado ou parte de stress conjunto.
- Se for isolado, cooldown se aplica antes de notificar (evita spam).
- Se for conjunto, notifica imediatamente (4-shock stress detectado).

### §7.5 Audit trail para todas as transições

Do `D3-AUTO-TRIGGER-SPEC.md` §7: **toda mudança de status** é registrada
em log imutável (S3 WORM, 7 anos retenção):

```sql
CREATE TABLE d3_audit_trail (
  id BIGSERIAL PRIMARY KEY,
  timestamp TIMESTPTZ NOT NULL,
  signal_id VARCHAR(50),       -- ex: 's1_vol30d'
  signal_value NUMERIC,
  rule_id VARCHAR(50),         -- ex: 'rule-002'
  action_type VARCHAR(50),     -- ex: 'TRIGGER', 'APPROVE', 'OVERRIDE'
  action_target VARCHAR(100),  -- ex: 's1_status'
  action_value VARCHAR(50),    -- ex: 'RED', 'CLUSTER_2'
  approver_id VARCHAR(50),
  approver_role VARCHAR(50),
  evidence_url TEXT,
  s3_checksum VARCHAR(64)
);
```

Compliance officer + Big 4 têm **read-only access** para auditoria.

### §7.6 Failure modes & recovery (do `D3-TRIGGER-MATRIX.md` §8)

| Failure mode | Recovery |
|---|---|
| False positive (trigger fires mas não é necessário) | CSO revisa em 24h, downgrade se confirmado; thresholds ajustados |
| False negative (trigger deveria ter fired mas não) | Head Supply/responsável reporta manualmente; trigger forçado via Slack |
| Script failure (auto-trigger quebra) | Alerta WhatsApp em 1h; CSO aciona manualmente; root cause em 24h |
| Approver unavailable (CEO viajando em RED) | Pre-delegation para CFO + Board Chair; CFO tem authority até R$ 200M |
